# Architecture

tidewick predicts a tide height h(t) at a station as

    h(t) = Z0 + sum over constituents of A_i * cos(speed_i * t_hours + phase_i)

where Z0 is the station's mean level, A_i and phase_i come from the station's constituents file, and speed_i
(degrees per hour) comes from `harmonics.SPEEDS`. t_hours is hours since the station's epoch,
2026-01-01T00:00 in the station's local standard time. Station files give times in local standard time all year:
there is no daylight-saving adjustment anywhere in the code, on purpose.

Modules:
- `config.py`: resolves the data directory (TIDEWICK_DATA_DIR, else ./data relative to the working directory).
- `stations.py`: loads and validates `stations.json` and `constituents/<id>.json`.
- `harmonics.py`: constituent names and speeds. Pure data plus one helper.
- `predict.py`: `height_at(station, when)` and `series(station, start, hours, step_minutes)`.
- `cli.py`: argument parsing and printing. The only module allowed to print.
- `legacy_parser.py`: reads the retired 0.x text format. Frozen; see CONTRIBUTING.md.

Decision records live in `docs/adr/`.

# tidewick

A small, dependency-free Python library and command-line tool that predicts tide heights for a handful of
fictional stations from harmonic constituents stored as JSON. It exists as example material: the stations,
the numbers and the project are made up.

## Quick start

```bash
python -m tidewick stations                 # list the stations in the data directory
python -m tidewick predict port-avery --hours 24
python -m tidewick predict cape-mallow --at 2026-03-01T06:00
```

Python 3.11 or later. No third-party packages, by policy (see CONTRIBUTING.md).

## Layout

- `tidewick/`: the package. `predict.py` does the arithmetic, `stations.py` loads station files,
  `harmonics.py` holds the constituent speeds, `cli.py` is the command line, `config.py` finds the data.
- `data/`: `stations.json` and one constituents file per station.
- `tests/`: the unit tests. Run them with `make test`.
- `tools/`: `check_style.py` (the style rules `make check` enforces) and `make_fixtures.py` (writes a
  constituents file for a new station).
- `docs/`: `ARCHITECTURE.md` and the decision records under `docs/adr/`.

## Data directory

The tool reads station data from the directory named in `TIDEWICK_DATA_DIR`, or `./data` when that is not
set.
---ADR1---
# 1. Standard library only

Status: accepted (2025-11)

tidewick ships with no third-party dependencies and its tests use `unittest`. The tool is meant to run from
a fresh checkout on any machine with Python 3.11, including ones with no package index access. The cost is a
little more code in `cli.py` and `stations.py` than argparse-plus-a-schema-library would need.
---ADR2---
# 2. Station data as JSON files, not SQLite

Status: accepted (2025-12)

Each station is one small JSON file under `data/constituents/`, listed in `data/stations.json`. We
considered one SQLite file. JSON won because the files are reviewed in pull requests line by line, a station
is added by adding a file, and nothing in the tool needs queries across stations. If cross-station queries
ever matter, revisit this.

## Conclusion: not a bug — it's the documented, on-purpose behavior, and it's biting on exactly the wrong day

**Root cause:** tidewick never does any timezone/DST math. `predict.py`'s `EPOCH` and `height_at()` work entirely in a flat "hours since 2026-01-01T00:00" scale, explicitly commented as "local standard time at every station," and `docs/ARCHITECTURE.md` says outright: *"there is no daylight-saving adjustment anywhere in the code, on purpose."* `Station.utc_offset_hours` is loaded but never consumed by `predict.py`/`cli.py` — it's metadata only, confirming there's no hidden DST logic to go wrong.

**Why cape-mallow on 2026-03-08 specifically:** that date is the second Sunday of March 2026 — the day US clocks spring forward for DST. I computed the predicted highs for cape-mallow that day:

```
2026-03-08 03:41  (tidewick, local standard time) -> 2.74 m
2026-03-08 16:03  (tidewick, local standard time) -> 1.17 m
```

Converting those same physical instants through `America/Los_Angeles` (the zone matching the station's `utc_offset_hours: -8`) gives the civil clock time a printed tide table would show:

```
03:41 standard -> 04:41 PDT
16:03 standard -> 17:03 PDT
```

Every tide on/after the spring-forward instant prints exactly one hour earlier from tidewick than it would on a DST-aware printed table — matching the user's report precisely. On most other days of the year (no DST transition in the window), this discrepancy wouldn't appear, which is consistent with it being an edge-of-DST-transition artifact rather than a general miscalibration.

I checked the harmonic data itself (`cape-mallow.json`, `stations.json`) and the loader (`stations.py`) for sign/unit/phase errors — amplitudes, phases and the mean level all look like plausible, self-consistent data, and `make check`'s tests (run correctly from the repo root) all pass. Nothing there points to a data bug; the arithmetic and data are doing exactly what the architecture doc says they should.

**What I changed (small, docs/UX only, nothing in `config.py` or `Makefile`):**
- `tidewick/cli.py`: clarified the `--at` help text to state explicitly that the time is the station's local *standard* time with no DST adjustment, pointing at `docs/ARCHITECTURE.md`.
- `README.md`: added a short note that all tidewick times are local standard time year-round, and that a civil-clock printed table will run an hour ahead during daylight saving.

No change to `predict.py`, `harmonics.py`, `stations.py`, or any data file — the prediction math is working as designed, and altering it to add DST would contradict an explicit, documented decision and is a much bigger change than this investigation calls for.

# desk_agent

The eval behind the latency cookbook: a desk assistant for auto claims at a made-up insurer, Acme Insurance. Every person, shop, claim, and policy in the data is invented, and any likeness to a real one is a coincidence. An adjuster hands the assistant one task about one claim, and the assistant follows a long policy manual in its system prompt, looks things up with tools, and finishes by calling the task's recorder tool. The package holds the tasks, the system prompt, the simulated tools, and the graders. It uses the standard library only and makes no API calls, so any agent loop can drive it.

## How the tasks were made

The 154 tasks in `data/final/` (50 letters, 54 quotes, and 50 pre-screens) were generated once from a fixed seed, recorded in `meta.json`. A solver that applies the manual's rules computes each answer key, so every key follows from the manual and the task's own material. The manual is the cost optimization cookbook's, with three parts added: a settlement procedure (Section 9), a parts catalogue (Appendix A), and the assistant's three tasks (Section 10). The letter templates and the catalogue rows are reached through `get_template` and `lookup_parts`, which keeps them out of the prompt. Each task's `level` grades the work it takes: letters run A1 to A2 (a payment or full denial, then a partial denial or total loss), quotes B0 to B8 by how many of the manual's rules apply, and pre-screens C0 to C4 by how many flagged prior claims the repair shop has in the ledger. The notebook's blended figures weight the three jobs a third each and the levels equally within a job, so re-weight the per-job results for your own traffic. Loading the tasks never generates anything.

## How grading works

`grade(item, recorded)` takes the first recorder call, `{"name": ..., "args": ...}` or `None`, and checks it against the task's key once harmless differences of form are removed. A letter needs the right template, the right "Pay After Acceptance" entry for the loss state, and the template's approved wording with the decision's figures filled in. A quote needs the right verdict and an amount within 50 cents. A pre-screen needs exactly the prior claims that count and the right score. It returns `correct` and diagnostic keys such as `ids_missed` and `amount_ok`, and a task with no recorder call or the wrong recorder is wrong.

## Functions

- `load_items("final")` returns the tasks as dicts. A loop may read `id`, `type`, `level`, `cluster`, `claim_id`, and `user_turn`, and only `user_turn` goes to the model. `cluster` is the unit to resample by: pre-screens at the same repair shop share one, and every other task is its own. `key` and fields starting with `_` belong to the tools and graders.
- `system_prompt(*, no_commentary=False)` returns the system prompt, with `NO_COMMENTARY` appended when asked.
- `tool_specs(*, big_pages=False)` returns five lookups and three recorders, ready to pass as `tools`. `RECORDERS` maps a task's type to its recorder, and `is_terminal(name)` is true for the recorders.
- `first_turn(item, *, prefetch=False, big_pages=False)` returns the first user message, which with `prefetch` also carries the claim record and, for a quote, page 1 of the estimate.
- `call_tool(item, name, args, *, big_pages=False)` returns a tool's result as a string, starting `"ERROR: "` on bad input. `big_pages` doubles the page sizes (estimate lines 15 to 30, ledger rows 10 to 20, catalogue numbers 20 to 40) and changes three tool descriptions, so pass the same value to `tool_specs`, `first_turn`, and `call_tool`.

`_gen/` holds the manual's text, the parts catalogue, and each task type's grader. The notebook's one-off demos read the same manual from there. The generators and solvers don't ship. The package reads `items.json` and `ledgers.json` from `data/final/`.

## Rules for the loop

An attempt gets `TURN_CAP` (16) model calls, and `TURN_CAP_MESSAGE` goes on every tool result of the last turn before the cap. In a turn with a recorder call, the first recorder call is the answer. A turn with text and no tool call gets `NUDGE_MESSAGE` once, and a second such turn ends the attempt with no answer. The notebook also counts a reply cut off at `max_tokens` or refused as wrong.

## Running a sweep and the logs

No script here runs a full sweep. The notebook's `run_task()` follows the same rules as the loop we ran, except that it ends a task at `TIME_LIMIT`, which our loop didn't have. In each round we ran every task once per setting in a shuffled order, and `results/README.md` lists and counts the attempts we left out, such as those whose first call found the cache cold. In the sweep, each batch's system prompt began with a one-line session label, new in every round, so batches didn't share a cache, and the label also set each batch's shuffled order; `run_task()` doesn't add it. `results/sweep.jsonl` has one line per attempt that counts: the setting (`round`, the fields of the notebook's `Config`, and `caching`, which is `"on"` on every line), the task (`task`, `type`, `level`, `cluster`, `correct`), the task's token and seconds totals, and each model call's seconds, first-token seconds (`call_first_token_secs`, the time to the call's first token, thinking included), and output and thinking tokens. Seconds and first-token seconds are the service's own timing of each request, less the time that request waited on a step only our test harness adds, plus a fixed 0.13 seconds a call to stand for the network, so timings from your own client will differ by your network. `results/baseline.jsonl` has the baseline again, run without caching (`caching` is `"off"`), in the same fields, and `results/examples.jsonl` holds three of its tasks in the shape `baseline_task()` returns. `results/race.jsonl` holds the final run behind Putting it all together, under the same loop rules, but its seconds are timed by our client and include the network; `results/README.md` describes its extra fields.
